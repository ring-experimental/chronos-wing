# 네트워크 기능 오프라인화

작성 2026-11-01. 원본은 TCP 서버(`210.222.18.18`)에 접속하는 네트워크 모드가 있다. 타이틀 메뉴 `네트워크`로 들어가고, 싱글의 동료와 용병으로 방어진을 짜 다른 플레이어의 비공정을 공략한다(`tdf/HELP`). 서비스가 끝나 이 모드 전체가 막혀 있다.

방식: `native/host/localnet.c`가 소켓 API를 받아 프로세스 안에서 응답한다. 게임의 UI와 처리 코드는 원본 그대로 돌고, 서버 역할만 C로 옮긴다. 기능별 처리기는 `native/host/localnet_<기능>.c`다. `캐시구입`(보우머)과 키냥냥 단축키는 `native/host/api.c`의 접속 처리에 이미 있어 여기서 다루지 않는다.

**분석 원칙: 응답에 담기는 값이 서버 고유 데이터인지 먼저 의심한다.** 유료상점 때 목록이 서버에 있다고 착각했는데 클라이언트 표에 다 있었다. 필드마다 클라이언트의 표, 파일(`DAT/`, `tdf/`, `ITM/`, `MAP/NT/`), 요청에 실려 오는 값, 세이브에서 나오는지 확인하고 근거 주소를 적는다. 다른 플레이어처럼 정말 서버에만 있던 데이터는 무엇을 근거로 만들었는지 적는다.

## 패킷

길이(be32, 머리 12바이트 포함), 대분류(be16), 소분류(be32), 결과(u8), 예비(u8), 본문. 최대 0x800바이트. 요청 작성은 `0x150348`(머리), `0x155818` u8, `0x155930` be16, `0x155998` be32, `0x1558d4` 바이트, `0x1503d8` 길이 확정, `0x156a18` 전송. 응답 읽기는 `0x155b28` s8, `0x155b84` s16, `0x155be8` be32, `0x155c70` be64, `0x155b04` 바이트. 라우터 `0x157ba8`. 처리기 대부분은 결과 0이 성공, -1이 실패이고 실패면 s16 길이 + EUC-KR 안내문이 이어진다.

응답 한 개를 받는 쪽은 `0x1566c8` 프레임 처리에서 큐를 비운다. 접속 진입은 `0x1579bc`이고 요청 종류를 `0x158a28`(값 `0x21004f`, 읽기 `0x158a54`), 결과를 `0x158a84`(값 `0x210035`, 읽기 `0x158ab0`)에 둔다. 연결 끊김 처리는 `0x157b1c`, 메시지 표시는 `0x157d84`다.

## 세션 (대분류 10, 4.1)

구현: `native/host/localnet_session.c`, `localnet_backup.c`(4.1만), 공통 상태 `localnet_state.c`. 2026-11-01 `work/saves/battle`로 시험했다.

### 진입 키

타이틀이 다 뜬 뒤(시작 후 약 10초) `ok`(메뉴) `down`(네트워크) `ok` `ok`(통화료 예) `ok`(테기, 리키는 팝업에서 `down` 후 `ok`) → 첫 접속이면 닉네임 입력(글자 키, `up`/`down` 모드, `ok`) → 공지 `ok` → 함선. 재접속은 서버 선택과 닉네임이 빠진다. 시작 직후에는 첫 `ok`가 페이드에 먹힐 수 있다. `run_test.sh`는 앞에 `wait4`를 넣는다. 함선에서 `clear`가 메뉴(전적, 주인공, 스킬, 소지품, 코스튬자랑, 시스템), 왼쪽 끝 키냥냥 대화가 NP 설명, 공격, 방어진관리 선택지다.

### 흐름

요청 종류(`0x158a54`): 타이틀 네트워크 1, 복구 3, 상인 캐시 4(`api.c`가 소켓 전에 가로챈다), 10 SMS 동의 시작. 종류 0, 1의 체인은 10.1 → (결과 -1이면 입력 칸, 10.2) → 4.1 → 10.4 → OK → 10.10 → `0x13f1a4(6,4)`.

- 10.1 `0x15040c`: 본문 전화번호 12(읽기 실패 때 게임이 만든 값), 2바이트, 버전 4(`v106`), 12바이트 0. 10.2는 같은 머리 뒤 닉네임 10. 판단은 `0x150770`: 0은 닉네임 10바이트 후 다음 단계, -1은 계정 없음(안내문은 로그만, 입력 칸은 `0x156ffc`), -2는 안내문을 띄우고 끊는 차단(플래그 NS+0x290a)이고 내장 서버는 쓰지 않는다.
- 4.1 `0x154884`는 응답 내용을 안 본다. 결과 0, -1 모두 10.4로 간다. 요청 본문은 `net/upload`에 그대로 둔다. 4.2 복구에 그대로 쓸 수 있다.
- 10.4: 개수 0을 보내면 안 된다. `0x150b30`이 공지 포인터를 만들지 않아 화면 `0x1574b4`가 0번지를 읽는다(폰은 통과, 여기서는 메모리 오류). 한 건을 보낸다. 개수는 최대 5(`0x158b38`).
- 10.10 `0x1505dc`: 직전에 `0x128278`, `0x143b70`이 표를 파일에서 다시 읽는다. 본문 주인공 +0x101, 8, (id be16, 레벨 u8) 8쌍.
- 10.5 점검(`0x150d60`), 10.6 방송(`0x150e80`)은 서버가 먼저 보내는 알림이라 보내지 않는다. 대분류 0(`0x15619c`)은 응답 없음이 맞다. 라우터 표 0번이 그냥 돌아간다(`0x157ba8`).

### 동료 `0x155210`, 표 `0x1a9e58`(0x74바이트, 10칸)

클라이언트 근거: 이름, 종류 +0x44, +0x48, +0x46은 `/DAT/SL`(`0x17ce14`), 소울링크 표시 +0, 경험치 +0x28, 필요 +0x2c(`0x17d144`: (L²-L+80)L), 레벨 +0x35는 세이브(`0x17cea8`). `/DAT/SL`의 8, 9번은 +0x48이 -1이고 10.10이 앞 8명만 보내는 이유다. id, 레벨은 10.10에서 얻는다. 이름은 요청 직전 다시 읽은 게스트 표에서 복사한다. 합류 여부는 동료 항목에 없고 스토리 변수로 판정한다(용병과 방어진 절의 "합류 판정").

**정정(2026-11-04):** +0(4.1 본문 오프셋 53부터 10바이트씩의 첫 바이트)을 합류로 읽었던 것은 틀렸다. 이 값은 현재 소울링크된 동료 한 명만 1이다(`0x104288`이 `0x17cff4`로 이전 동료를 0, `0x17cfec`로 새 동료를 1로 만든다. 세이브를 읽을 때 `0x1276b4`가 +0이 켜진 동료에게 링크를 다시 건다). 그래서 링크하지 않은 합류 동료가 모두 피로도 100, "아직 합류하지 않은 동료입니다"가 됐다. +0x40은 장착 장비 포인터다(`0x129204` 슬롯 6~15).

항목 순서: uid be64, id be16, 레벨 u8, 이름 길이 u8 + 이름, +0x4c be16(읽는 코드 못 찾음), 배치 +0x4e, +0x50, +0x52 be16(-1이면 미배치, 층=0x108 단위, `0x164b70`), 피로도 +0x4a u8(100이면 회색), be32와 u8(동료는 버리고 +0x54=1, +0x58=1, 용병은 계약 일, 시간), HP +0x24 be32, 개수 +0x5a u8, 값 be32 목록 +0x5c(첫 값이 공격력, 최대 3칸), 물리방어 +0x30, 마도방어 +0x32 be16, 치명타 +0x34 u8, +0x59 u8(읽는 코드 못 찾음). 화면 라벨은 `0x164584`.

HP, 공격력, 방어, 치명타는 클라이언트에서 찾지 못했다(나중에 찾았다. 용병과 방어진 절의 EMD/M). +0x46이 `NPC/D` 레코드 번호인데(1 엔지 ~ 8 보우머) 그 안의 수는 스프라이트와 부품 번호다(`0x159450`, `0x1599dc`). +0x48은 그 레코드의 마지막 값과 같다. 세이브에는 레벨과 경험치뿐이다. 모든 파일을 전수 조사한 것은 아니다. `member_stats`가 레벨로 만든 값(HP 100+40L, 공격력 10+4L, 방어 5+2L, 치명타 5%)이고 원본 공식이 아니다. uid 양수는 배치 비용 NS+0xf3c, 음수 구간은 용병 종류다(`0x164b70`: |uid|<0xf8은 0xf3b, -0x206~-0x104는 0xf3a). `/DAT/ML`의 id가 0xf8부터라 용병 uid는 그 음수로 보인다(확인 못 함).

배치 한도 NS+0xf38~0xf3e: 테기 서버는 12,3,2,1,1,1,3으로 고정(`0x150f40`), 리키 서버는 응답 끝 7바이트다. 같은 값을 보낸다. f38은 함선 전체, f39는 방 하나의 한도, f3a~f3c는 종류별 비용, f3d, f3e는 `0x165f00` 쪽 배치 수 제한이다(뒤 둘은 의미를 끝까지 따라가지 않았다).

### 서버 선택과 재시작

서버 종류는 게임이 OPT(`0x20d2d8`+0xb, `0x1480c4`가 `OPTDATA`에 저장)에 둔다. 1 테기, 2 리키. 프로필과 동료는 `net/profile`, `net/members`, 마지막 4.1은 `net/upload`다. 재시작 뒤 서버 선택과 닉네임 없이 함선까지 가는 것을 확인했다. `OPT +0x10`(`0x148318`)은 4.1, 10.4 요청 첫 값으로, 4.2 응답(`0x154be4`)이 쓴다.

### 공통 구조와 함정

- `localnet.h`의 `ln_me`, `ln_np_add`, `ln_np_spend`, `ln_fame_add`, `ln_write_profile`, `ln_members`, `ln_members_save`, `ln_write_members`, `ln_upload`, `ln_upload_joined`. 응답을 만들기 전에 값을 바꾸고 `ln_write_profile`로 쓴다. 대분류 1 이후 응답 일부는 NS 값을 직접 쓴다(예 `0x151d78` NP).
- 처리기가 false를 돌려주면 `localnet.c`가 연결을 끊는다. Read -1 → `0x156308` → `0x157b1c` 끊김 메시지 → OK로 타이틀. 응답 없는 대기는 게임에 시간 제한이 없어 영원히 데이터 요청중에 멈췄다. 처리기는 소분류를 모르면 false를 돌려주면 된다. 응답 없이 true를 돌려주면 멈춘다.
- 표 `0x1a9e58`은 네트워크 중 방어 부대 목록으로 덮어쓴다. 빈 칸(합류 안 한 동료 수만큼 뒤쪽)에는 `/DAT/SL` 이름이 남는다. `0x12b368`(`0x16265c`에서 호출)은 개수와 상관없이 8칸을 목록에 넣는다. 방어진 화면이 NS+0x28ce 개수를 지키는지 확인이 필요하다. 싱글로 돌아가면 게임이 파일에서 다시 읽는다(끊김 후 스토리 진입 확인).
- 목록의 +0x46, +0x44는 0x155210이 안 덮어 슬롯 값이 그대로다. 합류 동료만 앞으로 당겨 보내므로 어긋난다. 방어진에서 쓰는지 확인 못 했다.
- `MC_grpDrawString`, 입력기(표 4), TextComponent(표 9)가 비어 있어 닉네임 입력에서 죽었다. `host/ime.c`와 `gfx.c`에 넣었다. 입력 칸은 게임이 그리고 글자는 게임 글꼴 `0x12c1ec`로 그린다. `0x16265c`, `0x168a20`도 같은 입력 칸(`0x156ffc`)을 쓴다. 두 곳의 용도는 안 봤다.

### 4.2 복구 `0x154a8c` → `0x154be4`

요청은 본문이 없다. 응답은 4.1 본문(`0x154884`, 423바이트)과 필드 순서가 완전히 같다: be32 → OPT+0x10(`0x14833c`), 7바이트(버전 `V 1.0.6`, 응답은 버림), be32 세이브 읽은 길이(`0x143b70`, 0 이하면 나머지를 적용하지 않지만 완료 안내는 띄운다), 주인공 값, 동료 10칸, 3바이트 고정 표 64칸(0xd4 간격, 짐가방이 아니다. 정체 미확인. 첫 바이트는 올릴 때 +1, 받을 때 -1), 표 39칸. 그래서 올린 본문을 그대로 돌려준다. 서버에 따로 있던 값이 아니다. 적용은 게임이 한다(`0x1435d4(1)`, `0x127318`, `0x12e9a8(0,0)`로 지운 뒤 넣고 `0x145a40`, `0x1480c4`로 저장). 안내문 `캐릭터 복구가 완료되었습니다.`는 클라이언트에 있다. 결과 -1은 s16 길이 + 안내문을 띄우고 끊는다.

복구 자료는 `net/backup`이다. 4.1마다 세이브 길이가 0보다 크면 덮는다. 세이브 파일이 없는 새 설치(길이 0)의 값으로는 덮지 않는다. 자료가 없으면 결과 -1 `복구할 데이터가 없습니다.`(정한 문구). `net/upload`는 합류 판정(`ln_upload_joined`)에 쓰이므로 항상 마지막 값이다.

**도달 경로:** 요청 종류 3을 넣는 곳은 `0x14590c`, `0x145970` 둘뿐이고 둘 다 `0x1457d8`의 캐릭터 관리 메뉴 서브 상태 6, 7이다. 6은 서브 0(`캐릭터 복구` 팝업)에서만 간다(`0x145934`). 서브 0은 `restored/charmenu.c`가 .cwsave 팝업으로 바꿨으므로 **지금 빌드에서 4.2로 가는 경로는 없다.** 전체초기화(서브 3)는 `0x1483f0(0)`으로 서버를 지울 뿐이고, 다음 접속의 서버 선택(페이지 0xd, 안내 `처음 접속시 또는 전체초기화 후에만`)은 종류 1로 가는 일반 접속이다. 복구가 아니다. 7번 팝업(`복구와 동시에 앞으로 접속할 서버가 선택됩니다`)이 전체초기화 뒤 복구의 서버 선택이고 역시 서브 0을 거친다.

시험은 커밋하지 않은 임시 수정으로 `recover_popup`을 끄고 원본 팝업을 살려서 했다: 전체초기화 → 캐릭터 복구 → 예 → 통화료 예 → 서버 선택 → 완료 안내까지 확인. 복구 후 네트워크 접속의 4.1 본문이 `net/backup`과 바이트까지 같았다(복구된 값이 그대로 다시 올라온다). `net/backup`을 지우면 안내문이 뜨고 메뉴로 돌아간다.

한계: 전체초기화 뒤 복구 없이 네트워크로 들어가면 초기화된 캐릭터가 길이 0x198로 올라와(게임이 새 세이브를 쓴다) 복구 자료를 덮는다. 초기화된 값과 정상 값을 요청만으로 구분할 근거가 없어 그대로 뒀다. 원본 서버가 어떻게 했는지는 모른다.

### 4.3 코스튬 전송 `0x154ae4` → `0x154f50`

메뉴 `코스튬자랑`(페이지 7)에서 `#`이면 페이지 9(`0x120f0a`). `0x134918`이 흰 배경에 주인공을 그려 잘라낸 7000바이트(`0x1b58`) 그림을 만든다. 요청: u8 마지막 조각, be32 위치, be32 크기, 데이터. 1000바이트씩 7번이고 마지막 조각은 위치 6000이다(`0x122074`). NS 위치: +0x283c 버퍼, +0x2844 전체 크기, +0x2848 조각 크기, +0x284c 위치, +0x2850 마지막 표시.

그림 형식: 화면 정보(`GOT+0x2c`) +0x86이 1이면 화면 중앙 기준 (-35, -35)에서 70x50, RGB565 그대로. 2이면 50x70, 32비트에서 변환. 여기서는 1이다(그림으로 확인). 2는 시험 못 했다.

응답: 결과, s16 길이, 안내문. 조각마다 결과 0을 줘야 다음 조각을 보낸다(`0x158ab0`==1). 마지막 조각일 때만 안내문을 띄운다(`0x154f50`, NS+0x2850). -1이면 안내문 후 버퍼를 풀고 페이지 7로 돌아간다.

원본은 웹사이트(`HTTP://CWING.EAMOBILE.CO.KR`)에 올려 자랑하는 기능이다. 사이트가 없으므로 받은 그림을 저장 폴더 `net/costume.png`로 저장하고 성공을 준다. "현재 모습"을 올리는 기능이라 파일 하나를 덮어쓴다(정한 값). 안내문 `코스튬 그림을 저장했습니다.`, `코스튬 그림을 저장하지 못했습니다.`도 정한 값이다. 원본 문구는 서버에 있어 알 수 없다. 화면의 사이트 안내 문구는 원본 그대로 뒀다. 안내문은 소문자 영문을 피한다. 게임의 글꼴 함수에 `p`, `q`, `r` 같은 색 코드가 있어 경로를 넣으면 깨질 수 있다(코드를 따라가 확인하지는 않았다). PNG는 비압축으로 직접 쓴다(`png_encode`).

### 어디로 지급되는가

싱글 `캐시구입`은 `0x16a320`이 스킬/특성 초기화를 실행(`0x136340`, `0x1363c4`)하거나 짐가방에 넣는다(`0x13ad9c`). 네트워크 캐쉬샵에는 이 코드가 없다. 그래서:

|---|---|---|---|---|
| 8, 9 | 부활석 10, 20 | 500, 1000 | NT 창고 | 클라이언트 |
| 10 | 고대비약20 | 500 | NT 창고 | 클라이언트 |
| 11 | 허리주머니 | 500 | NT 창고 | 클라이언트 |
| 101 | NP 1000 | 1000 | `ln_np_add` | 정한 값 |
| 102 | 더블카운터 5개 | 1000 | `double_counter`, 최대 99 | 정한 값 |
| 103 | 보호쉴드 1일 | 1000 | `shield_min` | 정한 값 |
| 104 | SMS 알리미 10건 | 1000 | `net/sms_left` | 정한 값 |

- 코드 6, 7(초기화)은 뺐다. 실행 코드가 `0x16a320`뿐이고 사용 처리가 없어 창고에 넣어도 쓸 수 없다.
- 뒤 넷의 근거는 프로필 화면 `0x120ff8`의 `더블카운터`, `보호쉴드`와 `0x182be0`의 "SMS 알리미를 구매하세요"다. 이 값들을 쓰는 응답은 프로필과 1.33뿐이고 이름과 가격은 클라이언트에 없다. 수량, 가격, NP 상품은 내가 정했다. 원본 상품 구성은 모른다.
- `NP 회복`, `NP 보너스`, `자동보호`는 팔지 않는다. 표시만 있고 효과를 알 수 없다.
- 보호쉴드는 오프라인에 공격자가 없어 지금은 표시만 된다.
- 결제는 없다. 표시된 WON을 받지 않고 항상 성공이다. 원본에 재화 차감이 없으니(`0x1529e0`) NP는 빼지 않는다.

이름은 10바이트 안에서 끝낸다. 확인 창이 앞 10바이트만 그려 `고대비약 20개`가 `고대비약 2`로 나왔다. 수량은 이름이나 설명에 적었다.

### 저장과 다른 기능

`net/cash_delivery`: 4바이트 레코드(종류 u8, 번호 be16, 개수 u8), 최대 64건, 넘으면 실패 응답. `net/cash_shield`: 끝 시각 int64(epoch). `ln_cash_tick`이 `ln_write_profile` 때 `shield_min`을 다시 계산한다. `net/sms_left`: 남은 건수 int32.

- **NT 창고(`localnet_depot.c`)**: 3.1 때 `net/cash_delivery`를 읽어 자기 목록으로 옮기고 비워야 한다. 이게 없으면 구입품이 창고에 안 보인다.
- **SMS(`localnet_sleep.c`)**: 1.33(`0x152aec`의 be16)이 `net/sms_left`를 읽어 보내고 차감해야 한다.
- **더블카운터(`localnet_shadow.c`)**: 쓸 때 `double_counter`를 줄여야 한다.

### 시험

재접속 키 `wait4 ok down ok ok ok` 뒤 공지 `ok`. 걷기는 키를 0.09초 간격으로 여러 번 넣는다. 갑판에서 오른쪽 위 문으로 복도, 왼쪽 끝 문으로 선장실이다. 복도와 선장실 안쪽 위로 너무 가면 다른 문으로 빠진다. NPC는 왼쪽에 서서 `right` 후 `ok`로 말을 건다. 메뉴에서 `right right ok`가 캐쉬샵이다.

2026-11-01 `battle` 세이브로 확인: 목록 8건, 스크롤, 설명, 확인 창, 고대비약을 뺀 7개 상품의 구매와 지급 값, 안내문, 더블카운터 한도 실패 안내, 재시작 뒤 NP 2000과 저장 값 유지. 전적 화면에 `보호쉴드 1일`, `더블카운터 5개 남음`이 나온다. NT 창고 화면은 커밋하지 않은 임시 3.1 처리기로 `net/cash_delivery`를 넘겨 부활석 10과 허리주머니 아이콘, 설명까지 확인했다.

메뉴의 `소지금`은 NS 값이라 구입 직후에는 그대로고 10.13(전적) 또는 재접속 뒤 바뀐다. 1.41 응답에 프로필이 없어 원본도 같았을 것으로 본다.

### 세션 작업자의 함정 처리

`0x12b368`과 그리는 `0x1641fc`(0..8)는 개수를 안 보고 8칸을 쓰고, 10.10도 합류와 상관없이 8쌍을 보낸다. 그래서 원본 서버도 8명을 다 보냈다고 판단했다. **`ln_members_sync`가 이제 항상 슬롯 순서로 8칸을 보낸다.** 앞으로 당기지 않으므로 `0x155210`이 안 덮는 +0x44, +0x46이 어긋나지 않고, `/DAT/SL` 이름이 남는 빈 칸도 없다.

합류 안 한 동료는 피로도 100으로 보내 원본 화면이 회색, 전투불능으로 그리고 배치를 막게 했다. 합류하면 0으로 푼다. 원본이 어떻게 했는지 모른다(정한 값). 대사에 "소울링크로 육성한 동료"라고 나온다.

### 합류 판정

원본 서버가 받던 4.1, 10.10에는 합류 정보가 없다. 그래서 원본 서버가 어떻게 막았는지는 알 수 없고, 아래는 싱글 게임이 함선에 동료를 세우는 조건을 그대로 옮긴 것이다(`ln_members_sync`).

맵 스크립트 `/MAP/SC/NNN`(로더 `0x119a28`, 파서 `0x136a10`) 형식:
- 머리 9바이트(0~2는 각 절의 길이 폭, 1이면 u8 2면 u16). 9번째부터 절 A(개수, 길이들, 블록들), 절 B(같은 형식), 문자열 표.
- 절 A 블록은 객체다. 앞 7바이트가 x, y, 퀘스트 표시 변수, 외형(`NPC/D` 번호 = `/DAT/SL` +0x46), ?, ?, 시간대(6이면 항상). 생성은 `0x119f44`. 나머지는 이벤트 바이트코드(`0x136dac`): 0~0x7f는 B 블록 실행, `ff n 길이들 갈래들`은 조건이 맞는 첫 갈래, 0xfe 이하는 조건 `-2-op`(`0x11a054` 표). `f6 v x`는 스토리 변수 v가 x(`0x11ea0c`, 표 +0x7b4), `f5 v x`는 다른 변수표(+0x6b4), `fb`는 레벨, `fc`는 아이템 개수 등이다. A0이 맵에 들어올 때 실행된다.
- 절 B 블록은 명령 바이트코드(`0x13700c`, 처리 `0x11a2dc`, 0x57개). `ff a n (문자열, 길이)×n 본문들`은 선택지다. `22 v x`가 스토리 변수 설정(`0x11eac4`), `23 v x`가 다른 표, `03 n ff`가 객체 숨김, `38`이 대사, 동료 면담은 `4d` 리키, `43` 엔지, `4c` 레이, `41` 후거스, `49 n` 보우머, `47 n` 쟝(0)/펭(1)/팡(2)이다. 퀘스트는 시작 때 변수를 1, 완료 때 2로 둔다.
- 인자 길이표는 전체 1610블록을 모두 해석하는 것으로 맞췄다.

함선 방 A0(첫 갈래가 맞으면 끝): `SC/131` 리키, `SC/132` 엔지와 후거스, `SC/000` 레이와 보우머, `SC/129` 쟝, 펭, 팡. 동료 NPC가 남는 조건은 리키, 엔지, 후거스, 레이가 `v03 == 2`, 쟝과 펭이 `v05 == 2`, 보우머가 `v07 == 2`, 팡이 `v0f == 2`다. `vff == 2`(EXPERT)는 모두 남고, `v1d == 1`이고 `w23 == 1`인 동안(스토리 사건)과 엔지의 일부 구간(`v0f`만 2이고 `v16`, `v1c`, `v1f`, `v22`가 아닐 때)은 잠시 빠지지만 합류 판정에는 넣지 않았다.

네트워크 중에는 게임이 스토리 세이브를 읽지 않는다(`0x1436e8`이 `0x156d24`면 건너뛴다). 그래서 내장 서버가 `0x1849fc("MAINGAMEDATA", 버퍼, 1000)`로 직접 읽는다. 변수표는 13바이트(`0x17c2c0`), 35바이트(`0x1822a0`), +0x6b4 표 256바이트 뒤 오프셋 304다. 게임이 읽은 메모리 값과 256바이트가 같은 것을 확인했다. 파일이 없거나 해시가 맞지 않으면 모두 합류 전으로 본다. EXPERTDATA는 배치가 달라(`0x143914`) 읽지 않는다. EXPERT는 스토리를 끝내야 열리므로 MAINGAMEDATA가 있으면 이미 모두 2다.

시험(macOS, 2026-11-04): 폰 세이브 복사본은 8명 모두 합류(변수 03, 05, 07, 0f가 2), 방어진관리 목록 8칸 정상 표시, `net/members` 피로도 0. `work/saves/battle`은 0명, `work/saves/worldmap`은 엔지, 레이, 리키, 후거스만 합류. Android 실기기, 스토리 세이브를 지우고 EXPERT만 남긴 경우는 시험 안 함.

### 정한 값

클라이언트에 없다(찾아본 곳: `/DAT/*`, `tdf/*`, EMD/M, C3, 문자열).

- 기준 곡선(비율 100%): HP `52L-266`(최소 200), 물리방어 `3L/5+18`, 마도방어 `12L/25+10`, 공격력 `25L/4+32`. EMD/M 일반 몬스터(보스, 소환물 제외)의 레벨별 중앙값에 맞춘 직선이다. 원본 공식이 아니다.

### 시험과 미확인

재접속 뒤 함선에서 `left` 9번, `right` `ok`가 리키, 원형 메뉴 `right` `ok`가 방어진관리다(키냥냥 선택지는 설명만 나온다). 목록은 `right`가 용병 탭, `ok` `ok` `down` `ok`가 전투위치, `ok` `ok` `ok`가 배치, `clear` 4번 뒤 `clear`는 취소로 나가므로 수정이 있으면 `clear` 4번 `ok`다. 키냥냥 선택지의 `down`은 이번 시험에서 정상이었다.

### 정한 값

원본 값은 모른다. 모두 `localnet_shadow.c` 앞쪽이나 함수 한 줄에 있다.

- 가상 함장 32명: 이름, 길드 3개, 함선 문구 4개는 내가 지었다. 레벨은 순번으로 1~21 고정(`1+i*2/3`). 내 레벨이 올라도 위아래 상대가 남게 하려는 것이다. 명성치 초기값은 레벨²*40 + 작은 값이고, 내 승패로 변한다. 등급 이름은 레벨 1, 4, 8 구간 3개.
- 부대: 수 2 + 레벨/3(최대 6), 전부 갑판(층 0)의 6칸. 다층 배치는 문 통과를 시험하지 못해 쓰지 않았다. id는 `/DAT/SL` 8명, 함장 레벨 8 이상이면 홀수 번째를 `/DAT/ML` 앞 6종(uid 음수). 부대 레벨은 주인공 레벨 + (함장 레벨-내 네트워크 레벨)/2 + i%3 - 1. 네트워크 레벨만 쓰면 주인공이 약할 때 이길 수 없었다(주인공 레벨 2, 부대 레벨 15에서 한 대 48, 실패). 수치 공식은 세션 절 `member_stats`와 같다.
- 정산: 소모 20+레벨*10(2.1에서 빼므로 도중에 끊어도 돌려주지 않는다), 승리 NP 소모*2 + 레벨 차*20, 승리 명성 10+레벨 차*5(최소 2), 패배 명성 -2(0 아래로 안 감). 카운터, 더블카운터는 소모 0. 제한시간 170+레벨*5(최대 300).
- 검색: AT는 내 레벨 -3~+5에서 임의, RK는 명성 순, RV는 내 순위 위 4명부터, UR, GL은 부분 일치, DT는 등록 순. 데쓰노트 추가는 원본 요청대로 정확한 닉네임이고 24명까지. 내 RANK는 함장 중 나보다 명성이 높은 수 + 1이고 내 명성 합은 레벨별 fame_max 누적 + 현재 값이다.

### 가상 함장의 공격 (정한 동작)

공격 기록을 만들기로 했다. 근거: `tdf/HELP`가 실시간 침공을 게임의 축으로 설명하고, 없으면 2.3, 2.4, 2.5, 2.6과 프로필의 피격, 방어, 방어율, 피로도 소모가 영원히 쓰이지 않는다. `localnet.c`가 접속 유지(0,0)마다 `ln_shadow_tick`을 부른다. 접속 후 60초 뒤부터 30초마다 본다(로딩 화면에 팝업이 뜨는 것을 막으려고 넣었다).

- 6시간마다 한 건, 끊겨 있던 동안은 최대 3건. 마지막 건만 2.3으로 묻고 전투 중이면 경고만 뜬다.

## 휴면, SMS (1.30, 1.31, 1.33, 10.30)

구현: `native/host/localnet_sleep.c`, 상태는 `net/sleep`(끝나는 시각 둘, SMS 건수). 공통 수정: `ln_write_profile`이 `ln_sleep_tick`을 먼저 부른다. 프로필에는 남은 분만 있어 실제 시간이 흐른 것을 알 수 없기 때문이다.

### 화면 흐름 (`0x182540` 설정, `0x182710` 그리기, `0x182cd8` 진행, 상태 바이트 `0x211b38`)

네트워크 중 시스템 메뉴(`0x1823e8`)는 상태 값 1, 2, 7, 0xb, 3이고 이름은 `tdf/SMENU` 1, 2, 4, 5, 6번(환경설정, 도움말, 휴면설정, SMS알림, 접속종료)이다. 표: 설정 `0x9942c`, 그리기 `0x99484`, 키 `0x994c0`.

- 휴면: 7(1.30, 데이터 요청중) → 결과 1이면 8(기간 고르기) → 9(확인) → 0xa(1.31, 전송중) → 4(메뉴).
- SMS: 0xb(NS+0x23c를 -1로 두고 1.33 조회) → 결과 1이면 0xc(설정 화면) → 값이 바뀌었으면 0xd(확인) → 0xe(1.33 저장) → 4. 0xc에서 값이 그대로면 바로 4.
- 실패(-1)는 메시지 후 4.

### 1.30 기간 목록 `0x1525fc`

본문: 개수 u8, (이름 길이 u8, 이름, 값 u8)×개수. NS+0x2674 개수, +0x2675 이름 9바이트 단위, +0x2690 값. **최대 3개다.** 근거: 이름 포인터 표 `0x19ba48`이 3칸(`0x20fdcd`, `0x20fdd6`, `0x20fddf`, 데이터 재배치 값이라 코드에서 +0x2675는 응답 처리에만 보인다), 값 칸이 이름 바로 뒤, 초기화 0x20바이트. 창 높이(`0x1825c4`)도 개수 2, 3만 있고 나머지는 0이다. 그래서 1, 2, 4, 8시간 같은 4개 목록은 원본 형식에 들어가지 않는다.

**기간은 클라이언트 어디에도 없다.** `client.bin` 문자열, `tdf/`, `MAP/NT/`(글자 그대로 검색), `DAT`, `ITM` 모두 찾았다. 표시 함수 `0x158fc8`가 일/시간/분으로 나누므로 일 단위가 가능하다는 것만 안다. 정한 값: 8시간(값 8), 1일(24), 3일(72). 값은 시간이다.

### 원본 버그: 고른 기간이 요청에 안 실린다

`0x182606`(1.31 보내기)은 NS+0x2690+팝업`0x210778`의 +0x18을 읽는다. 그런데 상태 9가 같은 팝업을 예/아니오로 다시 만들며(`0x1826a0` → `0x1722b0` → `0x172230` → `0x11f018`) +0x18을 0으로 지운다. 예를 고른 시점(`0x182ec8`)이라 항상 0이다. 시험에서 `1일`을 고르고 보낸 값이 `08`이었다. 따라서 원본 클라이언트는 어느 항목을 골라도 첫 항목의 값을 보낸다. 서버는 고른 항목을 알 방법이 없다. 게임 코드는 건드리지 않았고, 안내문에 실제 기간을 적는다("8시간 휴면이 설정되었습니다."). 첫 항목 외 값(24, 72)의 처리는 코드로만 있고 화면으로는 못 탔다.

### 1.31 휴면 설정 `0x15277c`

요청: 값 s8. 응답: 안내문(be16 + EUC-KR)뿐이다. 0이면 게임이 NS+0x22c를 1로 두고 메시지를 띄운다. 남은 분과 NP는 안 받으므로 전적 화면을 열 때의 10.13에서 간다.

### 효과: 클라이언트는 표시만 한다

NS 기준으로 찾은 +0x22c 사용처는 `0x120ff8`(전적 표시), `0x15277c`, `0x155070`뿐이고, +0x244, +0x248도 `0x120ff8`, `0x120d8c`(표시), `0x155070`뿐이다. 공격, 검색, NP 코드는 이 값을 안 읽는다. 차단은 전부 서버 몫이었다. 설명문도 없다(`MAP/NT/000`의 NP 설명에 휴면 언급 없음).

- 실제 시간: 끝나는 시각을 `time()`으로 저장하고 남은 분을 10.10, 10.13 때 계산한다. 1초라도 남으면 1분. 끝나면 휴면 0, 남은 분 -1(표시 안 함). 게임을 끈 동안에도 흐른다. 기기 시계를 바꾸면 따라 바뀐다.
- 기간 중 변경 불가: 확인 문구("해당 기간동안에는 해제할 수 없습니다") 근거로 1.30, 1.31을 "휴면 중에는 변경할 수 없습니다."로 거절한다. 문구는 정한 값이다.
- 보호쉴드: 휴면 끝까지 늘린다. 근거 없이 정한 규칙이다. 공격 보호를 내 정보에서 보이게 하려는 것이다. 이미 더 길면 그대로 둔다.
- NP: 바꾸지 않는다. 1.31 응답에 NP가 없어(비교: `0x151d78` 쪽은 NS를 직접 쓴다) 비용이 있었다면 화면에 바로 안 나왔을 것이다. 약한 근거다.
- 공격 차단: `ln_is_protected()`, `ln_is_sleeping()`을 공략 기능에서 불러야 실제 효과가 난다. 휴면 중 내가 공격할 수 있는지는 근거가 없다.

### 1.33 SMS 설정 `0x152aec`, `0x1518dc`

요청: 값 s8. -1 조회, 0 둘 다 끔, 1 공격정보, 2 상태정보, 3 둘 다(`0x99468`, `0x182e74`). 응답: 0이면 설정 u8(+0x23c), 건수 s16(+0x23e), 안내문. 요청 전 +0x23c가 -1이면 안내문을 안 띄운다. 설정 -1이면 `0x182aae`가 "남은 SMS 알림 건수가 없습니다. SMS 알리미를 구매하세요."를 그리고 OK, 취소로 메뉴로 간다.

**남은 건수의 근거:** +0x23e를 쓰는 곳은 이 응답뿐이고(`0x152c30`), 읽는 곳은 `0x182aee`의 표시뿐이다. 프로필 `0x155070`, 구매 응답 `0x1529e0`에는 없다. 초기 건수는 클라이언트에 없고, 구매하라는 문구가 있으므로 0으로 정했다. 실제 문자를 못 보내므로 건수는 구매로만 늘고 줄지 않는다. 설정은 프로필 `sms`에 저장되어 재접속 뒤 남는다.

### SMS 알리미 구매 경로

클라이언트의 "SMS 알리미"는 위 안내문 한 곳뿐이고 상품 표가 없다. 구매 경로로 볼 곳은 메뉴 항목 `캐쉬샵`(`0x15c66c`, `0x15e68c`) → 1.40 목록(`0x1518a0`, `0x152890`) → 1.41 구매(`0x1518b8`, `0x1529e0`)다. 목록은 id, 이름, 설명, 가격 모두 서버가 준다(`0x15e528`). 캐쉬샵 처리기에서 상품을 넣고 구매 때 `ln_sms_add(건수)`를 불러야 한다. 원본 상품 구성은 모른다. 이 경로로 실제 사 본 시험은 안 했다.

### 10.30 SMS 수신 동의 `0x1506cc`, `0x151310`

OPT+9가 1이면(`0x148394`, 첫 설치 기본값 1 `0x14801c`~) 타이틀이 상태 0xb로 "EA MOBILE SMS 수신에 동의하시겠습니까?"를 띄운다(`0x1452e4`). 키 `0x1459aa`: 아니오는 NS+0x290c=0, OPT+9=0을 저장하고 끝(서버 안 감). 예는 NS+0x290c=1, 상태 0xc → 요청 종류 10으로 접속(`0x145476`) → 10.30(값 u8 + 0 29바이트). 결과 0이면 메시지와 결과 1 → OPT+9=0 저장, 실패면 1로 두어 다음에 다시 묻는다(`0x14575c`~). 내장 서버의 기존 처리로 끝까지 동작한다. 동의 값은 실제 발송에만 쓰일 값이라 저장하지 않는다. 로그인 없이 온다.

### 확인 못 한 것

Android, Windows 시험 안 함. 원본 기간과 건수 대조 불가. 캐쉬샵 진입과 구매 연동. 공격 차단은 공략 기능 병합 후에야 확인할 수 있다.
## 우편과 개인공지 (대분류 1, 소분류 1, 2, 3, 10, 11)

- 접속확인증: `ITM/DAT/66`의 첫 항목(종류 0x42, 번호 0), 설명이 "나에게 온 첫번째 편지!"다. `/DAT/QST`, `MAP/SC/000`의 퀘스트 `네트워크 접속`이 "네트워크 창고에서 접속확인증을 받아와봐"라고 한다. 서버의 첫 편지가 이것을 첨부했다고 보고, 첫 접속에 키냥냥 이름으로 한 통 넣었다(`add_welcome`). 읽으면 창고로 간다.
- `MAP/SC/000`, `MAP/SC/129`의 "네트워크에 접속하면 편지를 확인할 수 있습니다" 문구는 대사 옆 안내다. 어떤 편지인지 정할 근거가 파일에 없어 구현하지 않았다.

### 정한 값

- **읽으면 지운다.** 삭제 요청이 없고, 돌아갈 때 게임이 목록을 다시 받으며(`0x169f90`, 패킷료를 아끼는 게임이 내용이 안 바뀔 목록을 다시 받을 이유가 없다), 1.2 실패 경로도 같은 재요청을 하고, 공지 빈 문구가 "새로운 공지사항이 없습니다"다. 원본 동작이라는 직접 증거는 없다. 개인공지를 다시 볼 수 없으므로 공격 기록을 남겨 두고 싶으면 `notice_read`의 지우는 부분만 빼면 된다.
- **받는 사람.** 클라이언트에는 검증이 없고 실패 응답 경로만 있다. 플레이어가 혼자이므로 자기 닉네임이면 실제로 배달(돈과 아이템이 오간다), `ln_mail_add_name`으로 등록된 상대면 내용만 받고 끝, 그 밖은 "받는 사람을 찾을 수 없습니다."다. 상대는 실제 사람이 아니라서 돈과 아이템은 사라지기만 하므로 "돈과 아이템은 보낼 수 없는 상대입니다."로 거절한다. 상대가 답장하는 기능은 근거가 없어 넣지 않았다.
- 목록 제목은 `보낸이 : 내용 앞부분`이다. 원본 형식은 알 수 없다. 칸이 30바이트라 닉네임만은 아니었을 것이다.
- 편지 64통(가득 차면 발송 실패), 공지 64건(가득 차면 오래된 것 버림), 상대 이름 32개. 첫 편지 문구.

`localnet.h`에 `ln_notice_add`, `ln_mail_add_name`, `LN_ITEM_SIZE`, `ln_depot_take`, `ln_depot_put`을 추가했다.

### 시험과 미확인

`work/saves/battle`로 macOS에서 시험했다. 실제 `P` 표지판에서 메뉴와 받은편지 목록이 열리는 것을 봤다. 키는 함선에서 `right` 6번, `up up`, `left` 3번, `up`, `ok`인데 걷기가 키 타이밍에 흔들려 어긋날 때가 있다. 나머지 화면은 시험용 게임 폴더 복사본에서 표지판을 시작 위치 옆(9,9)으로 옮겨 봤다.

확인한 것: 첫 편지 읽기, 자신에게 돈+내용+아이템 발송과 수령(NP 1000→991→1000), 재시작 뒤 편지 유지, 없는 이름 실패 뒤 입력 유지, 등록 상대 발송, 등록 상대에게 돈 거절, 개인공지 목록, 쪽 넘김, 본문, 읽은 뒤 삭제, 창고 없을 때 첫 편지 수령 실패 안내. 아이템 첨부 왕복과 창고 화면은 **커밋하지 않은 임시 창고 코드**로만 시험했다. 실제 창고와 합친 시험은 하지 못했다. 다음은 못 봤다: 등록 상대에게 아이템 거절(돈과 같은 경로), 편지 쪽 넘김(공지와 같은 코드), 편지함 가득 참, `ln_notice_add`와 `ln_mail_add_name`을 실제 공략에서 부르는 경우(시험 때는 저장 파일에 직접 넣었다), 카운터 값의 실제 용도, Android와 Windows 빌드.
## NT 창고와 경매 (대분류 3)

| +0x1a | +0x180 | 목록은 팔레트 칸 수, 3.2와 3.3은 바이트 수(칸*2) |

| +0x58, +0x5c, +0x64 | | 경매만: 가격, 판매번호, 판매자 10바이트 |

- 3.1 `0x153d68`: u8 페이지 수(NS+0x28de, 제목 `%d/%d`), u8 NS+0x28df(읽는 코드 없음), u8 개수, 레코드. 요청은 페이지다.
- 3.2 `0x153974`: 레코드 값. 종류 8~10은 수치 8개, 11~12는 2개가 더 붙는데 내려줄 칸이 없고 게임이 id로 다시 합성하므로(`0x16dfc8`, id = 스킨*1000 + 스톤종류*100 + 스톤) 버린다.
- 3.3 `0x153b6c`: uid, 수량. 응답 `0x15409c`는 레코드와 팔레트. 물건은 게임이 목록 항목으로 자기 칸에 넣는다.
- 3.4 버림, 3.5 경매 등록(uid, 가격), 3.6 취소: 응답 `0x153f98`. 결과 0이면 안내문을 표시하지 않는다.
- 3.7 `0x153c34`: 동료 id, 아이템 id(-1 해제). 면담 화면의 `악세사리`로 종류 0x13이다(`0x15bbdc` → `0x11fa08(6)`). 응답 `0x1542a4`는 동료 전체 값 + 안내문.
- 3.8 `0x153c64`: 라우터 표(`0x153d18`) 8번에 처리기가 없고 게임도 기다리지 않는다. 응답을 보내지 않는 유일한 소분류다.
- 3.20 `0x153c7c`: 분류, 30, 페이지, 판매번호 be64. 응답 `0x1544f4`는 분류(`0x1584f8`), 개수(NS+0xbdd), 레코드, 다음 페이지 유무(NS+0xf36).
- 3.21 `0x153ce0`: 판매번호, 일련번호. 응답 `0x154760`은 새 NP(NS+0x1ec) + 안내문. 응답에 물건이 없으므로 산 물건은 NT 창고로 간다.

### 복제와 손실

올림: 게임이 3.2 응답을 받은 뒤 자기 칸에서 지우고 저장하고 3.8을 같은 프레임에 보낸다(`0x13c2c0`). 그래서 3.2는 메모리에만 넣고 3.8에서 저장한다. 3.2와 응답 사이에 꺼지면 물건은 싱글에 남고 창고에는 없다. 저장 직후 3.8 전에 꺼지면 잃는데 같은 프레임 안이다.
내림: 3.3 처리에서 바로 지우고 저장한다. 프로토콜에 확인 통보가 없어 응답 처리 전 몇 프레임 안에 꺼지면 그 물건은 잃는다. 복제 쪽은 막혀 있다.
경매 중 물건은 게임이 막고(`0x13e2e0`) 서버도 3.3, 3.4를 거절한다.

### 클라이언트에 있던 것

- 필터 분류: 이름표 `0x9b320`(판매번호검색, 쌍수, 대검, 마력, 투구, 갑옷, 주, 젬, 골, 장갑, 신발, 목걸이, 반지, 귀걸이, 옵션스크롤). 번호와 파일의 대응은 코드에 없어 내용으로 맞췄다: 1~5 → 3~7(이름이 `스킨`으로 나온다), 6~8 → 0~2(0번은 화면에서 `주`와 `마도스톤` 설명 확인, 1, 2번은 순서로 추정), 9~10 → 13~14, 11~13 → 15~17, 14 → 71.
- 물건 이름, 설명, 기준 가격: `/ITM/DAT/%02d`. 형식은 `0x137654`, `0x1377a0`. 3~71번 전부 파일 끝까지 맞는 것을 확인했다. 0~2번은 앞 16바이트 해시 뒤가 암호문이고 `0x105908`로 푼다.
- 옵션스크롤 값 범위: 표 `GOT+0x514`, 항목 0x24, +0x1c~+0x1d(`0x12bbfc`).
- 안내문 `경매중인...`(`0x936fc`), `경매장에 등록할수...`(`0x93650`).

### 정한 값 (서버에만 있었다)

- 창고 5페이지 150칸. 칸 수는 화면 6×5에서 왔고 페이지 수는 정했다.
- 등록 가능 종류: 필터에 분류가 있는 종류만. 분류가 없으면 찾을 수 없기 때문이다. 합성 장비(8~12)는 등록 불가다.
- 시장: 분류마다 가격이 0이 아닌 물건 중 날짜와 종류, id의 해시로 12개. 같은 날은 같은 목록이고 산 물건은 그날 빠진다(`net/market`, 하루 64건 한도). 수량 1, 옵션 없음(`0x1372dc` 초기값), 스크롤 값은 범위 가운데.
- 가격: 표 가격/10을 기준 NP로 하고 80~120%, 10 단위, 최소 10. 표 가격과 NP의 환율은 클라이언트에 없다. 첫 NP 1000으로 일부를 살 수 있는 정도로 골랐다.
- 판매자 이름 8개, 판매번호(시장은 100000 + 종류*1000 + id, 내 물건은 uid).
- 판매번호는 화면에 표시되는 곳을 찾지 못했다. 검색은 동작한다.

### 내 물건이 팔리는 흐름: 만들었다

근거: 경매 등록이 NP를 버는 유일한 용도인데 다른 플레이어가 없으면 영원히 안 팔린다. 반면 클라이언트에 판매 완료 문구나 전용 응답은 없어(`낙찰`, `수수료` 문자열 없음) 원본의 정산 방식은 모른다. 우편 첨부 NP(`r%d pNP`)로 왔을 가능성이 있지만 확인 못 했다.
규칙: 등록 후 24시간이 지났고 가격이 기준 NP*수량의 70% 이하면 3.1, 3.20 때 팔린다. 시장 최저가가 기준의 80%이므로 사서 되팔아 NP를 불릴 수 없다. 표 가격이 0인 물건은 안 팔린다. 입금은 `ln_np_add`에 NS+0x1ec도 맞춘다. 알림은 없고 목록에서 사라진다. 비싸게 올리면 안 팔리고 취소로 돌려받는다.

### 확인 못 한 것

- 3.7: `battle`에 합류 동료와 종류 0x13 장비가 없어(`교체할 장비가 없습니다`) 실행 못 했다. 응답 형식만 맞췄다. 동료 수치는 정한 값이고 요청에 장비 수치가 없어 교체해도 수치가 안 변한다. 장비 효과가 전투에 반영되는지 모른다.
- 합성 장비(종류 8~12)와 염색 팔레트 올림/내림, 수량 2 이상의 일부 내림, 2페이지 이상, 창고 가득 참, 스크롤을 실제로 부여하기.
- 3.1은 우편 첨부 화면(`0x168a20`, NS+0x28f5)도 쓴다. 첨부한 물건을 창고에서 빼는 일은 우편 쪽이 `depot_find`, `depot_remove`, `depot_save`로 해야 한다.
- Android, Windows 빌드.

## 통합

`offline/net-all`에 기능 브랜치를 합치며 앞 절의 "병합 때 맞출 지점"을 이었다. 앞 절에 남은 병합 전 설명보다 이 절이 우선한다.

- 캐쉬샵의 보호쉴드, SMS 알리미는 `ln_shield_add`, `ln_sms_add`를 쓴다. `net/cash_shield`, `net/sms_left`, `ln_cash_tick`은 없앴다.
- NT 창고 목록(3.1)이 `net/cash_delivery`를 창고로 옮긴다. 우편 첨부는 `ln_depot_take`, `ln_depot_put`을 쓴다. 염색품과 경매 중인 물건은 첨부할 수 없다(25바이트 형식에 팔레트 내용이 없다).
- 공략 전적은 `ln_notice_add`로 개인공지에 남는다. 가상 함장 이름은 편지 받는 사람으로 등록한다. 내 함선 전장과 피로도는 `ln_defense`, `ln_write_defense`, `ln_unit_fatigue_add`를 써서 용병도 포함한다. 휴면과 보호쉴드 중에는 가상 공격이 오지 않는다.

통합 빌드에서 확인: 첫 접속, 첫 편지 수령 뒤 접속확인증이 창고에 들어감, 지급 대기 2건이 창고 화면에 나타남(대기 파일은 직접 넣었다), 가상 공격 팝업과 개인공지 기록, 반격 전투 진입. `make windows`는 빌드만 했다.

## 입력 칸

원본 칸은 폰 키패드 전제라 `host/ime.c`의 나랏글 입력을 없애고 플랫폼 입력기로 바꿨다. 칸이 열리면(`0x20d927`) `SDL_StartTextInput`을 켜고, 받은 글자를 EUC-KR로 바꿔 칸(`0x20d638`)에 직접 넣는다. 조합 중인 글자는 칸에 보이기만 한다. 이름 칸은 최대값이 14지만 패킷이 10바이트라 10바이트로 막는다. 글꼴과 KS X 1001에 없는 글자는 버린다. 영문은 원본처럼 대문자가 된다. `상,하:전환` 안내와 모드 표시는 원본 그대로 남아 있지만 뜻이 없다. 제어 파일 `text <글자>`, `edit <글자>`로 시험한다.

한글 조합 수정(2026-11-01). 게임의 키 입력은 틱마다 한 칸(`0x1593b0`)이라, 입력기가 조합할 때 보내는 Backspace + 새 글자의 순서가 뒤집혔다. Backspace를 `host/ime.c`에서 칸에 바로 적용하고, 칸이 비었을 때만 게임의 취소로 넘긴다. 칸에 못 넣은 글자는 세어 두어 그만큼의 Backspace는 칸을 지우지 않는다. 첫가끝 자모도 음절로 합친다. 2026-11-01 사용자가 한글 입력이 잘 된다고 확인했다(앞서 문제를 보고한 macOS 로컬 빌드와 Android 폰).
