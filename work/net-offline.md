# 네트워크 기능 오프라인화

작성 2026-11-01. 원본은 TCP 서버(`210.222.18.18`)에 접속하는 네트워크 모드가 있다. 타이틀 메뉴 `네트워크`로 들어가고, 싱글의 동료와 용병으로 방어진을 짜 다른 플레이어의 비공정을 공략한다(`tdf/HELP`). 서비스가 끝나 이 모드 전체가 막혀 있다.

방식: `native/host/localnet.c`가 소켓 API를 받아 프로세스 안에서 응답한다. 게임의 UI와 처리 코드는 원본 그대로 돌고, 서버 역할만 C로 옮긴다. 기능별 처리기는 `native/host/localnet_<기능>.c`다. `캐시구입`(보우머)과 키냥냥 단축키는 `native/host/api.c`의 접속 처리에 이미 있어 여기서 다루지 않는다.

**분석 원칙: 응답에 담기는 값이 서버 고유 데이터인지 먼저 의심한다.** 유료상점 때 목록이 서버에 있다고 착각했는데 클라이언트 표에 다 있었다. 필드마다 클라이언트의 표, 파일(`DAT/`, `tdf/`, `ITM/`, `MAP/NT/`), 요청에 실려 오는 값, 세이브에서 나오는지 확인하고 근거 주소를 적는다. 다른 플레이어처럼 정말 서버에만 있던 데이터는 무엇을 근거로 만들었는지 적는다.

## 패킷

길이(be32, 머리 12바이트 포함), 대분류(be16), 소분류(be32), 결과(u8), 예비(u8), 본문. 최대 0x800바이트. 요청 작성은 `0x150348`(머리), `0x155818` u8, `0x155930` be16, `0x155998` be32, `0x1558d4` 바이트, `0x1503d8` 길이 확정, `0x156a18` 전송. 응답 읽기는 `0x155b28` s8, `0x155b84` s16, `0x155be8` be32, `0x155c70` be64, `0x155b04` 바이트. 라우터 `0x157ba8`. 처리기 대부분은 결과 0이 성공, -1이 실패이고 실패면 s16 길이 + EUC-KR 안내문이 이어진다.

응답 한 개를 받는 쪽은 `0x1566c8` 프레임 처리에서 큐를 비운다. 접속 진입은 `0x1579bc`이고 요청 종류를 `0x158a28`(값 `0x21004f`, 읽기 `0x158a54`), 결과를 `0x158a84`(값 `0x210035`, 읽기 `0x158ab0`)에 둔다. 연결 끊김 처리는 `0x157b1c`, 메시지 표시는 `0x157d84`다.

## 세션 (대분류 10, 4.1)

구현: `native/host/localnet_session.c`, `localnet_backup.c`(4.1만), 공통 상태 `localnet_state.c`. 2026-11-01 `work/saves/battle`로 시험했다.

### 진입 키

타이틀이 다 뜬 뒤(시작 후 약 10초) `ok`(메뉴) `down`(네트워크) `ok` `ok`(통화료 예) `ok`(테기, 리키는 팝업에서 `down` 후 `ok`) → 첫 접속이면 닉네임 입력(글자 키, `up`/`down` 모드, `ok`) → 공지 `ok` → 함선. 재접속은 서버 선택과 닉네임이 빠진다. 시작 직후에는 첫 `ok`가 페이드에 먹힐 수 있다. `run_test.sh`는 앞에 `wait4`를 넣는다. 함선에서 `clear`가 메뉴(전적, 주인공, 스킬, 소지품, 코스튬자랑, 시스템), 왼쪽 끝 키냥냥 대화가 NP 설명, 공격, 방어진관리 선택지다.

### 흐름

요청 종류(`0x158a54`): 타이틀 네트워크 1, 복구 3, 상인 캐시 4(`api.c`가 소켓 전에 가로챈다), 10 SMS 동의 시작. 종류 0, 1의 체인은 10.1 → (결과 -1이면 입력 칸, 10.2) → 4.1 → 10.4 → OK → 10.10 → `0x13f1a4(6,4)`.

- 10.1 `0x15040c`: 본문 전화번호 12(읽기 실패 때 게임이 만든 값), 2바이트, 버전 4(`v106`), 12바이트 0. 10.2는 같은 머리 뒤 닉네임 10. 판단은 `0x150770`: 0은 닉네임 10바이트 후 다음 단계, -1은 계정 없음(안내문은 로그만, 입력 칸은 `0x156ffc`), -2는 안내문을 띄우고 끊는 차단(플래그 NS+0x290a)이고 내장 서버는 쓰지 않는다.
- 4.1 `0x154884`는 응답 내용을 안 본다. 결과 0, -1 모두 10.4로 간다. 요청 본문은 `net/upload`에 그대로 둔다. 4.2 복구에 그대로 쓸 수 있다.
- 10.4: 개수 0을 보내면 안 된다. `0x150b30`이 공지 포인터를 만들지 않아 화면 `0x1574b4`가 0번지를 읽는다(폰은 통과, 여기서는 메모리 오류). 한 건을 보낸다. 개수는 최대 5(`0x158b38`).
- 10.10 `0x1505dc`: 직전에 `0x128278`, `0x143b70`이 표를 파일에서 다시 읽는다. 본문 주인공 +0x101, 8, (id be16, 레벨 u8) 8쌍.
- 10.5 점검(`0x150d60`), 10.6 방송(`0x150e80`)은 서버가 먼저 보내는 알림이라 보내지 않는다. 대분류 0(`0x15619c`)은 응답 없음이 맞다. 라우터 표 0번이 그냥 돌아간다(`0x157ba8`).

### 동료 `0x155210`, 표 `0x1a9e58`(0x74바이트, 10칸)

클라이언트 근거: 이름, 종류 +0x44, +0x48, +0x46은 `/DAT/SL`(`0x17ce14`), 합류 +0, 경험치 +0x28, 필요 +0x2c(`0x17d144`: (L²-L+80)L), 레벨 +0x35는 세이브(`0x17cea8`). `/DAT/SL`의 8, 9번은 +0x48이 -1이고 10.10이 앞 8명만 보내는 이유다. id, 레벨은 10.10, 합류 여부는 4.1 본문(오프셋 53부터 10바이트씩: 합류, 경험치, 필요, 레벨)에서 얻는다. 이름은 요청 직전 다시 읽은 게스트 표에서 복사한다.

항목 순서: uid be64, id be16, 레벨 u8, 이름 길이 u8 + 이름, +0x4c be16(읽는 코드 못 찾음), 배치 +0x4e, +0x50, +0x52 be16(-1이면 미배치, 층=0x108 단위, `0x164b70`), 피로도 +0x4a u8(100이면 회색), be32와 u8(동료는 버리고 +0x54=1, +0x58=1, 용병은 계약 일, 시간), HP +0x24 be32, 개수 +0x5a u8, 값 be32 목록 +0x5c(첫 값이 공격력, 최대 3칸), 물리방어 +0x30, 마도방어 +0x32 be16, 치명타 +0x34 u8, +0x59 u8(읽는 코드 못 찾음). 화면 라벨은 `0x164584`.

HP, 공격력, 방어, 치명타는 클라이언트에서 찾지 못했다. +0x46이 `NPC/D` 레코드 번호인데(1 엔지 ~ 8 보우머) 그 안의 수는 스프라이트와 부품 번호다(`0x159450`, `0x1599dc`). +0x48은 그 레코드의 마지막 값과 같다. 세이브에는 레벨과 경험치뿐이다. 모든 파일을 전수 조사한 것은 아니다. `member_stats`가 레벨로 만든 값(HP 100+40L, 공격력 10+4L, 방어 5+2L, 치명타 5%)이고 원본 공식이 아니다. uid 양수는 배치 비용 NS+0xf3c, 음수 구간은 용병 종류다(`0x164b70`: |uid|<0xf8은 0xf3b, -0x206~-0x104는 0xf3a). `/DAT/ML`의 id가 0xf8부터라 용병 uid는 그 음수로 보인다(확인 못 함).

배치 한도 NS+0xf38~0xf3e: 테기 서버는 12,3,2,1,1,1,3으로 고정(`0x150f40`), 리키 서버는 응답 끝 7바이트다. 같은 값을 보낸다. f38은 함선 전체, f39는 방 하나의 한도, f3a~f3c는 종류별 비용, f3d, f3e는 `0x165f00` 쪽 배치 수 제한이다(뒤 둘은 의미를 끝까지 따라가지 않았다).

### 서버 선택과 재시작

서버 종류는 게임이 OPT(`0x20d2d8`+0xb, `0x1480c4`가 `OPTDATA`에 저장)에 둔다. 1 테기, 2 리키. 프로필과 동료는 `net/profile`, `net/members`, 마지막 4.1은 `net/upload`다. 재시작 뒤 서버 선택과 닉네임 없이 함선까지 가는 것을 확인했다. `OPT +0x10`(`0x148318`)은 4.1, 10.4 요청 첫 값으로, 4.2 응답(`0x154be4`)이 쓴다.

### 공통 구조와 함정

- `localnet.h`의 `ln_me`, `ln_np_add`, `ln_np_spend`, `ln_fame_add`, `ln_write_profile`, `ln_members`, `ln_members_save`, `ln_write_members`, `ln_upload`, `ln_upload_joined`. 응답을 만들기 전에 값을 바꾸고 `ln_write_profile`로 쓴다. 대분류 1 이후 응답 일부는 NS 값을 직접 쓴다(예 `0x151d78` NP).
- 처리기가 false를 돌려주면 `localnet.c`가 연결을 끊는다. Read -1 → `0x156308` → `0x157b1c` 끊김 메시지 → OK로 타이틀. 응답 없는 대기는 게임에 시간 제한이 없어 영원히 데이터 요청중에 멈췄다. 처리기는 소분류를 모르면 false를 돌려주면 된다. 응답 없이 true를 돌려주면 멈춘다.
- 표 `0x1a9e58`은 네트워크 중 방어 부대 목록으로 덮어쓴다. 빈 칸(합류 안 한 동료 수만큼 뒤쪽)에는 `/DAT/SL` 이름이 남는다. `0x12b368`(`0x16265c`에서 호출)은 개수와 상관없이 8칸을 목록에 넣는다. 방어진 화면이 NS+0x28ce 개수를 지키는지 확인이 필요하다. 싱글로 돌아가면 게임이 파일에서 다시 읽는다(끊김 후 스토리 진입 확인).
- 목록의 +0x46, +0x44는 0x155210이 안 덮어 슬롯 값이 그대로다. 합류 동료만 앞으로 당겨 보내므로 어긋난다. 방어진에서 쓰는지 확인 못 했다.
- `MC_grpDrawString`, 입력기(표 4), TextComponent(표 9)가 비어 있어 닉네임 입력에서 죽었다. `host/ime.c`와 `gfx.c`에 넣었다. 입력 칸은 게임이 그리고 글자는 게임 글꼴 `0x12c1ec`로 그린다. `0x16265c`, `0x168a20`도 같은 입력 칸(`0x156ffc`)을 쓴다. 두 곳의 용도는 안 봤다.
- 입력 키 배열은 원본 폰 배열을 알 수 없어 정했다. 영문 2~9 멀티탭, 숫자 그대로, 한글 1 ㄱㅋㄲ 2 ㄴㄹ 3 ㄷㅌㄸ 4 ㅂㅍㅃ 5 ㅅㅎㅆ 6 ㅈㅊㅉ 7 ㅇㅁ 8 ㅏㅓㅑㅕㅐㅔㅒㅖ 9 ㅗㅜㅛㅠ 0 ㅡㅣ, 1초 안에 같은 키면 순환. 겹받침은 없다.

### 4.2 복구 `0x154a8c` → `0x154be4`

요청은 본문이 없다. 응답은 4.1 본문(`0x154884`, 423바이트)과 필드 순서가 완전히 같다: be32 → OPT+0x10(`0x14833c`), 7바이트(버전 `V 1.0.6`, 응답은 버림), be32 세이브 읽은 길이(`0x143b70`, 0 이하면 나머지를 적용하지 않지만 완료 안내는 띄운다), 주인공 값, 동료 10칸, 소지품 64칸(첫 바이트는 올릴 때 +1, 받을 때 -1), 표 39칸. 그래서 올린 본문을 그대로 돌려준다. 서버에 따로 있던 값이 아니다. 적용은 게임이 한다(`0x1435d4(1)`, `0x127318`, `0x12e9a8(0,0)`로 지운 뒤 넣고 `0x145a40`, `0x1480c4`로 저장). 안내문 `캐릭터 복구가 완료되었습니다.`는 클라이언트에 있다. 결과 -1은 s16 길이 + 안내문을 띄우고 끊는다.

복구 자료는 `net/backup`이다. 4.1마다 세이브 길이가 0보다 크면 덮는다. 세이브 파일이 없는 새 설치(길이 0)의 값으로는 덮지 않는다. 자료가 없으면 결과 -1 `복구할 데이터가 없습니다.`(정한 문구). `net/upload`는 합류 판정(`ln_upload_joined`)에 쓰이므로 항상 마지막 값이다.

**도달 경로:** 요청 종류 3을 넣는 곳은 `0x14590c`, `0x145970` 둘뿐이고 둘 다 `0x1457d8`의 캐릭터 관리 메뉴 서브 상태 6, 7이다. 6은 서브 0(`캐릭터 복구` 팝업)에서만 간다(`0x145934`). 서브 0은 `restored/charmenu.c`가 .cwsave 팝업으로 바꿨으므로 **지금 빌드에서 4.2로 가는 경로는 없다.** 전체초기화(서브 3)는 `0x1483f0(0)`으로 서버를 지울 뿐이고, 다음 접속의 서버 선택(페이지 0xd, 안내 `처음 접속시 또는 전체초기화 후에만`)은 종류 1로 가는 일반 접속이다. 복구가 아니다. 7번 팝업(`복구와 동시에 앞으로 접속할 서버가 선택됩니다`)이 전체초기화 뒤 복구의 서버 선택이고 역시 서브 0을 거친다.

시험은 커밋하지 않은 임시 수정으로 `recover_popup`을 끄고 원본 팝업을 살려서 했다: 전체초기화 → 캐릭터 복구 → 예 → 통화료 예 → 서버 선택 → 완료 안내까지 확인. 복구 후 네트워크 접속의 4.1 본문이 `net/backup`과 바이트까지 같았다(복구된 값이 그대로 다시 올라온다). `net/backup`을 지우면 안내문이 뜨고 메뉴로 돌아간다.

한계: 전체초기화 뒤 복구 없이 네트워크로 들어가면 초기화된 캐릭터가 길이 0x198로 올라와(게임이 새 세이브를 쓴다) 복구 자료를 덮는다. 초기화된 값과 정상 값을 요청만으로 구분할 근거가 없어 그대로 뒀다. 원본 서버가 어떻게 했는지는 모른다.

### 4.3 코스튬 전송 `0x154ae4` → `0x154f50`

메뉴 `코스튬자랑`(페이지 7)에서 `#`이면 페이지 9(`0x120f0a`). `0x134918`이 흰 배경에 주인공을 그려 잘라낸 7000바이트(`0x1b58`) 그림을 만든다. 요청: u8 마지막 조각, be32 위치, be32 크기, 데이터. 1000바이트씩 7번이고 마지막 조각은 위치 6000이다(`0x122074`). NS 위치: +0x283c 버퍼, +0x2844 전체 크기, +0x2848 조각 크기, +0x284c 위치, +0x2850 마지막 표시.

응답: 결과, s16 길이, 안내문. 조각마다 결과 0을 줘야 다음 조각을 보낸다(`0x158ab0`==1). 마지막 조각일 때만 안내문을 띄운다(`0x154f50`, NS+0x2850). -1이면 안내문 후 버퍼를 풀고 페이지 7로 돌아간다.

원본은 웹사이트(`HTTP://CWING.EAMOBILE.CO.KR`)에 올려 자랑하는 기능이다. 사이트가 없으므로 받은 그림을 저장 폴더 `net/costume.png`로 저장하고 성공을 준다. "현재 모습"을 올리는 기능이라 파일 하나를 덮어쓴다(정한 값). 안내문 `코스튬 그림을 저장했습니다.`, `코스튬 그림을 저장하지 못했습니다.`도 정한 값이다. 원본 문구는 서버에 있어 알 수 없다. 화면의 사이트 안내 문구는 원본 그대로 뒀다. 안내문은 소문자 영문을 피한다. 게임의 글꼴 함수에 `p`, `q`, `r` 같은 색 코드가 있어 경로를 넣으면 깨질 수 있다(코드를 따라가 확인하지는 않았다). ## 휴면, SMS (1.30, 1.31, 1.33, 10.30)

### 화면 흐름 (`0x182540` 설정, `0x182710` 그리기, `0x182cd8` 진행, 상태 바이트 `0x211b38`)

네트워크 중 시스템 메뉴(`0x1823e8`)는 상태 값 1, 2, 7, 0xb, 3이고 이름은 `tdf/SMENU` 1, 2, 4, 5, 6번(환경설정, 도움말, 휴면설정, SMS알림, 접속종료)이다. 표: 설정 `0x9942c`, 그리기 `0x99484`, 키 `0x994c0`.

- 휴면: 7(1.30, 데이터 요청중) → 결과 1이면 8(기간 고르기) → 9(확인) → 0xa(1.31, 전송중) → 4(메뉴).
- SMS: 0xb(NS+0x23c를 -1로 두고 1.33 조회) → 결과 1이면 0xc(설정 화면) → 값이 바뀌었으면 0xd(확인) → 0xe(1.33 저장) → 4. 0xc에서 값이 그대로면 바로 4.
- 실패(-1)는 메시지 후 4.

### 1.30 기간 목록 `0x1525fc`

본문: 개수 u8, (이름 길이 u8, 이름, 값 u8)×개수. NS+0x2674 개수, +0x2675 이름 9바이트 단위, +0x2690 값. **최대 3개다.** 근거: 이름 포인터 표 `0x19ba48`이 3칸(`0x20fdcd`, `0x20fdd6`, `0x20fddf`, 데이터 재배치 값이라 코드에서 +0x2675는 응답 처리에만 보인다), 값 칸이 이름 바로 뒤, 초기화 0x20바이트. 창 높이(`0x1825c4`)도 개수 2, 3만 있고 나머지는 0이다. 그래서 1, 2, 4, 8시간 같은 4개 목록은 원본 형식에 들어가지 않는다.

**기간은 클라이언트 어디에도 없다.** `client.bin` 문자열, `tdf/`, `MAP/NT/`(글자 그대로 검색), `DAT`, `ITM` 모두 찾았다. 표시 함수 `0x158fc8`가 일/시간/분으로 나누므로 일 단위가 가능하다는 것만 안다. 정한 값: 8시간(값 8), 1일(24), 3일(72). 값은 시간이다.

### 원본 버그: 고른 기간이 요청에 안 실린다

`0x182606`(1.31 보내기)은 NS+0x2690+팝업`0x210778`의 +0x18을 읽는다. 그런데 상태 9가 같은 팝업을 예/아니오로 다시 만들며(`0x1826a0` → `0x1722b0` → `0x172230` → `0x11f018`) +0x18을 0으로 지운다. 예를 고른 시점(`0x182ec8`)이라 항상 0이다. 시험에서 `1일`을 고르고 보낸 값이 `08`이었다. 따라서 원본 클라이언트는 어느 항목을 골라도 첫 항목의 값을 보낸다. 서버는 고른 항목을 알 방법이 없다. 게임 코드는 건드리지 않았고, 안내문에 실제 기간을 적는다("8시간 휴면이 설정되었습니다."). 첫 항목 외 값(24, 72)의 처리는 코드로만 있고 화면으로는 못 탔다.

### 1.31 휴면 설정 `0x15277c`

요청: 값 s8. 응답: 안내문(be16 + EUC-KR)뿐이다. 0이면 게임이 NS+0x22c를 1로 두고 메시지를 띄운다. 남은 분과 NP는 안 받으므로 전적 화면을 열 때의 10.13에서 간다.

### 효과: 클라이언트는 표시만 한다

NS 기준으로 찾은 +0x22c 사용처는 `0x120ff8`(전적 표시), `0x15277c`, `0x155070`뿐이고, +0x244, +0x248도 `0x120ff8`, `0x120d8c`(표시), `0x155070`뿐이다. 공격, 검색, NP 코드는 이 값을 안 읽는다. 차단은 전부 서버 몫이었다. 설명문도 없다(`MAP/NT/000`의 NP 설명에 휴면 언급 없음).

- 실제 시간: 끝나는 시각을 `time()`으로 저장하고 남은 분을 10.10, 10.13 때 계산한다. 1초라도 남으면 1분. 끝나면 휴면 0, 남은 분 -1(표시 안 함). 게임을 끈 동안에도 흐른다. 기기 시계를 바꾸면 따라 바뀐다.
- 기간 중 변경 불가: 확인 문구("해당 기간동안에는 해제할 수 없습니다") 근거로 1.30, 1.31을 "휴면 중에는 변경할 수 없습니다."로 거절한다. 문구는 정한 값이다.
- 보호쉴드: 휴면 끝까지 늘린다. 근거 없이 정한 규칙이다. 공격 보호를 내 정보에서 보이게 하려는 것이다. 이미 더 길면 그대로 둔다.
- NP: 바꾸지 않는다. 1.31 응답에 NP가 없어(비교: `0x151d78` 쪽은 NS를 직접 쓴다) 비용이 있었다면 화면에 바로 안 나왔을 것이다. 약한 근거다.
- 공격 차단: `ln_is_protected()`, `ln_is_sleeping()`을 공략 기능에서 불러야 실제 효과가 난다. 휴면 중 내가 공격할 수 있는지는 근거가 없다.

### 1.33 SMS 설정 `0x152aec`, `0x1518dc`

요청: 값 s8. -1 조회, 0 둘 다 끔, 1 공격정보, 2 상태정보, 3 둘 다(`0x99468`, `0x182e74`). 응답: 0이면 설정 u8(+0x23c), 건수 s16(+0x23e), 안내문. 요청 전 +0x23c가 -1이면 안내문을 안 띄운다. 설정 -1이면 `0x182aae`가 "남은 SMS 알림 건수가 없습니다. SMS 알리미를 구매하세요."를 그리고 OK, 취소로 메뉴로 간다.

**남은 건수의 근거:** +0x23e를 쓰는 곳은 이 응답뿐이고(`0x152c30`), 읽는 곳은 `0x182aee`의 표시뿐이다. 프로필 `0x155070`, 구매 응답 `0x1529e0`에는 없다. 초기 건수는 클라이언트에 없고, 구매하라는 문구가 있으므로 0으로 정했다. 실제 문자를 못 보내므로 건수는 구매로만 늘고 줄지 않는다. 설정은 프로필 `sms`에 저장되어 재접속 뒤 남는다.

### SMS 알리미 구매 경로

클라이언트의 "SMS 알리미"는 위 안내문 한 곳뿐이고 상품 표가 없다. 구매 경로로 볼 곳은 메뉴 항목 `캐쉬샵`(`0x15c66c`, `0x15e68c`) → 1.40 목록(`0x1518a0`, `0x152890`) → 1.41 구매(`0x1518b8`, `0x1529e0`)다. 목록은 id, 이름, 설명, 가격 모두 서버가 준다(`0x15e528`). 캐쉬샵 처리기에서 상품을 넣고 구매 때 `ln_sms_add(건수)`를 불러야 한다. 원본 상품 구성은 모른다. 이 경로로 실제 사 본 시험은 안 했다.

### 10.30 SMS 수신 동의 `0x1506cc`, `0x151310`

OPT+9가 1이면(`0x148394`, 첫 설치 기본값 1 `0x14801c`~) 타이틀이 상태 0xb로 "EA MOBILE SMS 수신에 동의하시겠습니까?"를 띄운다(`0x1452e4`). 키 `0x1459aa`: 아니오는 NS+0x290c=0, OPT+9=0을 저장하고 끝(서버 안 감). 예는 NS+0x290c=1, 상태 0xc → 요청 종류 10으로 접속(`0x145476`) → 10.30(값 u8 + 0 29바이트). 결과 0이면 메시지와 결과 1 → OPT+9=0 저장, 실패면 1로 두어 다음에 다시 묻는다(`0x14575c`~). 내장 서버의 기존 처리로 끝까지 동작한다. 동의 값은 실제 발송에만 쓰일 값이라 저장하지 않는다. 로그인 없이 온다.

### 확인 못 한 것

Android, Windows 시험 안 함. 원본 기간과 건수 대조 불가. 캐쉬샵 진입과 구매 연동. 공격 차단은 공략 기능 병합 후에야 확인할 수 있다.
